### Diagnostic (lecture seule)

Lu dans le code (ancien `mirror-github-packages.mjs`) :

- `exists(registry)` lance `npm view <nom>@<version> version --registry <registre>` et renvoie `false` sur **toute** exception, `true` si la commande réussit. Un 401, un 403, un 500 ou un délai valent « absent » ; un succès vaut « présent » sans contrôle de la source.
- `onNpm` interroge `https://registry.npmjs.org/`, `onGithub` interroge `https://npm.pkg.github.com`, tous deux par `--registry`.
- `skipReason` : privé, puis « pas encore publié sur npmjs » si `onNpm` est faux, puis « déjà sur GitHub Packages » si `onGithub` est vrai. Un `onNpm` faux est un **ignoré**, jamais un échec : le job reste vert avec huit paquets non traités.

- `release.yml` : `setup-node` avec `registry-url: https://npm.pkg.github.com`, `NODE_AUTH_TOKEN` = `GITHUB_TOKEN`, `timeout-minutes: 10`.

Supposé, non établi `[À VÉRIFIER]` (aucun accès au registre ni aux journaux du run) :

- `setup-node` écrit dans `.npmrc` la ligne `registry=` et, la portée valant par défaut le propriétaire, `@paulperigault:registry=https://npm.pkg.github.com/` (documentation de l'action, non relue ici) ; npm donne priorité à un registre de portée sur `--registry`. Si c'est vrai, `onNpm` et `onGithub` interrogeaient le même registre.
- Si GitHub répond 200 à `npm view` pour un paquet qu'il n'héberge pas (relais vers npmjs), cela explique « déjà sur GitHub Packages » sans publication, et l'ordre des deux runs (18:14 : `tokens` seul propagé ; 20:42 : tous). La page de GitHub lue le 2026-11-04 ne décrit pas ce relais.
